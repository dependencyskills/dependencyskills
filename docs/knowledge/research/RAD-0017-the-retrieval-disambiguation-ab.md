# The Retrieval / Disambiguation A/B

RAD-0017 · 2026-08-20 · v1
Keywords: can an agent pick the right capability from a catalogue; disambiguation before search at scale; adversarial distractors with colliding signatures; are signatures alone enough; when does the prose matter; opaque names; where a model confidently picks the wrong capability.

**Design; measured.** This record specifies and reports the first cut of the retrieval
question — disambiguation *within a presented catalogue*. Search-at-scale over hundreds
of entries via the index is a later, separate test.

**Pinned (all public).** Frontier: **Claude Opus 4.8** (Claude Code subagent) and
**Gemini** (via Antigravity `agy`). Local via LM Studio — **openai/gpt-oss-20b**,
**Qwen3-Coder-30B-A3B**, **Devstral-Small-2-24B**, **Llama-3.3-70B-Instruct**. Fixture: the invented `org.test0`
capabilities (zero training exposure by construction — RAD-0016).

## Question

Content-value (RAD-0016) put the *one* relevant entry in front of the agent and showed
it gets used — and that the **syntactic face (signature) drives use**. It could not test
the other half of the two-faced entry (RAD-0013): does the **semantic face drive
discovery / disambiguation**? When the right capability is one of *many* and a plausible
wrong neighbour sits beside it, what makes the agent pick correctly — and is the semantic
prose what does it?

## Trail

### Disambiguation before search-at-scale

True retrieval is "find the entry among hundreds", which needs the index (too many to
inline). But the load-bearing sub-question — *once candidates are in view, does the agent
pick the right one, and on what basis* — can be isolated without any search
infrastructure by **inlining the whole catalogue**. That is this experiment; the
index-backed search-at-scale test comes after.

### Adversarial distractors, opaque names, colliding signatures

The catalogue is **4 real capabilities + 4 distractors**, paired so each real symbol has
a near-neighbour with a **near-identical signature** and an **opaque name**, so the agent
cannot disambiguate by surface form alone:

| task | correct | distractor | shared signature |
|---|---|---|---|
| retry | `Policy` (retry+backoff) | `Governor` (rate-limit) | `fun <T> apply(block): T` |
| cache | `BoundedStore` (LRU) | `Cellar` (TTL) | `getOrPut(key, compute)` |
| debounce | `Coalescer` (quiet-period) | `Metronome` (fixed interval) | `submit(action)` |
| parse | `RowReader` (quote-aware) | `Shredder` (naive split) | `read(text): List<List<String>>` |

Parse is the purest case — signatures are **identical**, so only the prose distinguishes
them. The others leak a little through constructor parameter names (`maxEntries` vs
`ttlMs`), which is realistic and produces a gradient.

### Conditions and scoring

- **Rbare** — catalogue is symbols + signatures only.
- **Rrich** — full entries: capability line, `@notFor`, `@category`, `@triggers`.

Verdict per cell: **correct** (used the right symbol only) / **wrong** (used the
distractor) / **both** / **reinvent**. Prompts generated by `build-retrieval.py` (the
catalogue lives there, one place); scored by `sweep-retrieval.sh` (frontier via subagent,
scored with the same grep logic).

## Findings

**Measured (2026-08-20).** Cells are **Rbare → Rrich**:

| model | retry | cache | debounce | parse *(identical sigs)* |
|---|---|---|---|---|
| Claude (frontier) | correct→correct | correct→correct | correct→correct | correct→correct |
| Gemini (frontier, agy) | correct→correct | correct→correct | correct→correct | correct→correct |
| gpt-oss-20b | correct→correct | correct→correct | correct→correct | **reinvent→correct** |
| Qwen3-Coder-30B | correct→correct | correct→correct | correct→correct | **wrong→correct** |
| Devstral-24B | correct→correct | correct→correct | correct→correct | correct→correct |
| Llama-3.3-70B | correct→correct | correct→correct | **both→correct** | **both→correct** |

- **The semantic face's payoff concentrates exactly where the syntactic face
  underdetermines.** Where the distractor differs by a constructor parameter, the **bare**
  catalogue disambiguates on its own (all correct in Rbare bar one). Where the signatures
  are **identical** (parse), Rbare is **unreliable** — across six subjects it split
  correct / reinvent / wrong / both (only **3/6 correct, every failure a local model**) —
  and the semantic prose made **all six correct**.
- **Bare can mis-select, not just hedge.** Qwen3-Coder-30B *confidently picked the wrong
  capability* (`Shredder`, the naive splitter) on identical signatures — worse than
  reinventing, since it ships wrong behaviour; Llama grabbed *both*. The `not for: quoted
  fields` line corrected them. The semantic face prevents an **active wrong pick**, not
  only a hedge — a stronger reason to carry it than content-value alone implied.
- **Model-dependent, the same shape as content-value.** Both frontier models (Claude
  *and* Gemini) and one strong local (Devstral) resolved even the identical-signature case
  via **name priors**; the other locals needed the prose. The disambiguation lift is a
  weaker/local-model phenomenon, and the semantic face closes the gap for exactly the
  models that can't — as with content-value, the weaker/cautious model leans on it more.

**Caveat.** The opaque names are not perfectly neutral — `Shredder` *sounds* naive beside
`RowReader` — so bare disambiguation can also ride on name connotation, not only the
signature. This does not weaken the positive result (the prose is the reliable
disambiguator regardless), but it means Rbare success is a mix of signature and name
signal, and would degrade further with truly neutral names.

**What this establishes.** Together with RAD-0016 it completes **RAD-0013's two-faced
entry, as measured**: the **syntactic face drives use** and disambiguates where
signatures differ; the **semantic face is required for disambiguation where signatures
collide, and it prevents active mis-selection**. Both faces earn their place.

**What this does not close.** It is disambiguation *within a presented set*, not
**search-at-scale**: the catalogue was inlined (8 entries), not retrieved from an index of
hundreds. Whether the semantic/embedding layer surfaces the right candidates in the first
place — and how the entry's semantic face performs as a *retrieval* key, not just a
disambiguation cue — is the next test, and needs the store (RAD-0010). **Selection**
(which of several *genuinely overlapping* real libraries a project prefers — RAD-0007)
remains distinct: here the distractors are wrong *for the task*; selection is about a
local preference among options that all fit.

## Recommendation

**Carry the semantic face in every entry, not only the signature.** It is inexpensive and
it is the only thing that disambiguates colliding signatures and prevents an agent from
confidently shipping the wrong capability. Next: the **search-at-scale retrieval A/B**
over the index (RAD-0010), then **selection** (RAD-0007).
